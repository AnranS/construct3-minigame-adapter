# Troubleshooting

First identify whether the problem occurs during plugin initialization, export inspection, mini-game compilation, engine startup, or an application API call. Keep the complete error, tool version, actual base-library logs, and minimal reproduction steps. This is usually more useful than repeatedly changing compilation options.

This page preserves the real WeChat validation records from 0.2.0 and explains the limits of integrations added in the current {{VERSION}} release. The known WeChat IDE Modal Worker error is still unresolved. A dialog displaying normally does not mean that error has disappeared.

## No mini-game export option after installing the plugin

This is how the tool currently works. MiniGameBridge provides platform calls through event sheets and JavaScript, while the offline CLI converts the export. The plugin does not register a new exporter in Construct's export menu.

Select **HTML5 export** in Construct, extract the ZIP, then run `inspect` and `convert --experimental`. Full commands are in [Quick start](../guide/).

## UNSUPPORTED in browser preview

An ordinary browser has neither the native WeChat `wx`, Douyin `tt`, or TikTok `TTMinis.game` host nor the bridge installed by the converter. Validate platform APIs in a converted mini-game project.

If you are already in a mini-game IDE, check that you imported the converter's output directory and that `game.js` runs correctly. Then inspect the API with `supportsAPI` or `getCapabilities`. An API is unavailable if its name is outside the directory, it is not registered for this platform, both its native method and explicit fallback are missing, or the directory requires an `off...` method that is missing. Explicitly registered global-off / no-off exceptions use their local deactivation contracts.

Do not suppress this error with simulated success callbacks. Have the interface clearly report that the feature is unavailable in the current environment.

## NOT_READY, WRONG_API_KIND, or JSON errors

| Symptom | Action |
| --- | --- |
| `NOT_READY` | Call Init first and perform application operations after On ready |
| `WRONG_API_KIND` | Use the [API directory](../api/) to choose Call API, a synchronous call, an object factory, or an event subscription |
| `INVALID_JSON` | Check for valid JSON: strings need double quotes and trailing commas are not allowed |
| `INVALID_ARGUMENT` | Call API takes an options object; Read synchronous API takes an array of positional arguments |
| Success with an empty `LastResultJSON` | Check `LastResultIsJSON` / `LastResultType`; obtain native undefined values, bytes, or handles through JavaScript |

An API with the same name can have different kinds on WeChat and Douyin, such as `shareAppMessage`. See [Plugin integration](../addon/) for result expressions and tag rules.

## CLI cannot read input or refuses to overwrite

The CLI accepts an extracted HTML5 directory. If the input is a `.c3p`, a ZIP, a directory at the wrong level, or an export missing scripts or resources, correct the input before building.

```sh
node src/cli.mjs inspect --input ./exports/my-game
```

Check every `error` in the inspection report. Converting a Construct project requires an explicit `--experimental` flag; it does not bypass other inspection failures.

For a valid same-platform `--overwrite`, omitting `--appid` preserves its previous value, along with `libVersion` and valid private configuration. Omitting it for a first build or a different platform leaves it empty. An explicit `--appid` replaces the old value, and an explicit empty string clears it. If the old configuration, marker, or report used to identify the platform is corrupt, overwrite is refused and the old output is preserved. First verify the file contents and which project the output belongs to.

Output must not overlap with input. Existing output needs its `.c3-minigame-output.json` marker and `--overwrite`; otherwise use a new empty directory. Do not disguise an arbitrary existing directory as output generated by this tool.

The tool rejects input symlinks, modules outside the export directory, remotely executable scripts, general HTML inline scripts, and unbundled bare-package dependencies. Organize game dependencies into a complete local export. Do not delete files that are still referenced merely to pass inspection.

## Build succeeds, but the screen is blank or ready never arrives

Distinguish these three states:

| State | What it establishes |
| --- | --- |
| CLI build succeeds | File-structure processing and bundling completed |
| `__C3MiniGameLoaded` | Entry scripts have loaded |
| `[C3 MiniGame] Construct runtime-ready` | Construct's actual ready message has been handled |

Check the first game-related console error. Confirm that the imported directory contains `game.js` and `game.json`, that resource paths are complete, and that the AppID and project type are correct. Do not focus only on the last cascading error.

Run the repository's MiniGameApiSuite first, then gradually add your own objects, audio, effects, and third-party plugins. This adapter provides limited DOM, resource, network, and audio interfaces, not a complete browser. Arbitrary HTML plugins, WebGPU, and complete browser audio effect chains are outside the current validated scope.

After changing the IDE's device configuration or base-library version, fully reopen the project before observing the result. In this test round, the iPhone 12 and iPad Pro 12.9 simulators both displayed correctly after a full reopen. Not every dynamic-resize path has passed acceptance testing.

## jsbridge not ready during startup

In this test round, WeChat base libraries 3.17.3 / 3.17.2 were observed reporting this from `WAGame.js` before the game entry ran:

```text
[jsbridge] invoke getSystemInfo fail: jsbridge not ready
```

The current validation baseline uses 3.15.3. If a similar startup error occurs, select this baseline in the developer tools, clear the console display, and **fully reopen the project**. Check the actual `Wechat Lib` version in the new logs, then inspect `runtime-ready` and the rendered screen.

The version selected in the settings panel and the error suffix do not necessarily establish that an existing context has switched versions. During this test round, old-version logs remained after selecting a new version; the change was confirmed only after a full reopen. Reopening the project does not require clearing game storage.

This is a local version-comparison result, not a claim that every project or client has the same issue, or a recommendation to pin one version permanently. Validate the final target base library separately for your project.

## Modal triggers worker path empty

**Status: still unresolved.** The issue reproduced in WeChat Developer Tools RC 2.02.2607161 with base library 3.15.3 and, after a full reopen, 3.12.1. The updated sample's native dialog, confirmation, and cancellation callbacks work while the red Worker error still occurs.

Reproduce and record it as follows:

1. Fully reopen MiniGameApiSuite and confirm the base-library version and Construct `runtime-ready` in the new logs.
2. Open the native interface category and select Modal.
3. Test confirmation and cancellation separately, recording return values and console errors.
4. In the Network panel, check whether the internal `worker.js` request includes `libName=WAAccelerateWorker.js`.

Local read-only source analysis and an isolated function reproduction traced the issue to query parameters being lost when the IDE forwards an internal Worker request. This is a local investigation finding that has not been confirmed officially; no validated IDE fix has been delivered. Downgrading to 3.12.1 did not remove the error either.

Do not add an empty application `workers` directory as a fix, suppress the error, or replace the native dialog with simulated success. Retest against an official corrected release or submit a minimal reproduction to the vendor. Whether physical devices are affected is still unverified.

## Network, login, or ad failures

A capability result of `supported: true` means only that the current host exposes a callable method. The application operation can still fail.

| Capability | Project configuration to check |
| --- | --- |
| HTTPS / download / upload | Allowed platform domains, certificates, service reachability, HTTP status, and application response |
| WebSocket | WSS URL, platform domains, subprotocols, and server handshake; successful SocketTask creation does not mean onOpen occurred |
| Login | Native temporary code, your server-side exchange flow, failure handling, and expiry handling |
| Rewarded video | Actual ad placement, platform enablement, and ad inventory; grant a reward only after explicit complete viewing |
| Location, recording, photo library, etc. | Permissions, platform privacy configuration, user actions, and scene requirements |
| Open data / leaderboards | Corresponding context and permission settings, and the permitted calls in the main and open-data contexts |

When ad, external HTTPS, or WebSocket parameters are empty in the sample, it reports missing configuration instead of initiating calls. Supply your own project configuration, then record success, failure, and cancellation paths for these features separately.

## Storage, audio, or input problems

Native storage uses project-specific keys. Verify writing, reading, and deletion first, then persistence after restart. The general native `clearStorage` affects that native storage space and is not an appropriate first step for diagnosing startup issues.

Audio must use resources that exist in the package and are supported by the platform. Check native `onError`, validate playback, stopping, and natural completion separately, and release objects and listeners when the feature closes. This test round verified explicit stopping, resource release, and natural `onEnded` for an eight-second test clip. Complete decoder and effect-chain behavior requires separate validation.

If input coordinates or page dimensions are wrong, fully reopen the current device configuration and compare with the minimal sample. Touch and wheel adapters have automated regression coverage. Those results do not replace actual validation of the latest wheel forwarding, physical-device multitouch, or hardware behavior.

## Debugging tools and MCP

This project's actual acceptance checks used the developer-tool UI, console, and Network panel. The community `wechat-dev-mcp` project was investigated, but the current project does not depend on it. A successful MCP connection is not treated as proof that the game started.

The official IDE CLI installed during this test round exposes tools such as `get_simulator_console` and `get_simulator_network`, but calls depend on the IDE service-port setting. `IDE service port disabled` means that debugging channel is disabled, not that the game failed to compile. You can continue debugging in the IDE console without being required to enable that port to run this project.

When filing an issue, include the tool and base-library versions, Construct version, build report, minimal reproduction, first error, and platform. Remove temporary login codes, user input, personal storage contents, and private project credentials. See [Validation records](../validation/) for completed and pending checks.

## TikTok startup reports offWindowResize is required

The old adapter required both `on...` and `off...` methods for internal events. A user's TikTok iOS physical-device error showed that the host exposed `onWindowResize` but not `offWindowResize`, causing the old build to stop during adapter installation.

Update the source and reconvert the HTML5 export. The fixed TikTok adapter uses a shared event dispatcher when `on...` exists but `off...` is missing. Disposing of the adapter removes its own local callbacks, and repeated installation reuses the same native listener without affecting other callers. When a corresponding `off...` exists, native unsubscription is still used. This compatibility logic covers startup listeners for window, input, foreground/background, and network events. It adds no fake native methods and does not expand the public API directory.

Local regressions passed for startup with missing off methods, window updates, disposal, reinstallation, and a complete bundled fixture. These are local tests. Later fix4 user screenshots provided page-display and category-navigation evidence; see below for the exact limits and storage failure. Consult TikTok's official [Event](https://developers.tiktok.com/docs/en/mini-games-sdk-event) and [Device and Network](https://developers.tiktok.com/docs/en/mini-games-sdk-device-and-network) references for native API scope instead of inferring support from WeChat or Douyin names.

## TikTok shows a gray screen with only a secure context warning

A TikTok iOS user reported on 2026-09-21 that `fix1` no longer threw the `offWindowResize` exception, but the game still showed a gray screen. The last game-related log was Construct's `not a secure context` warning, and the Error page was empty. The failure stage was unknown at that point. Later physical-device logs from `fix2` identified a `queueMicrotask` receiver error. Subsequent `fix4` screenshots showed the API page and navigation into the storage category, providing partial rendering and navigation evidence while exposing a storage read-back failure. See the handling below.

That warning does not itself stop Construct startup. A confirmed diagnostic gap was that the Construct constructor returns immediately after starting asynchronous initialization. Later failures in the initialization Promise could bypass the entry-load error handler for `__C3MiniGameLoaded`. An empty Error page can therefore coexist with an initialization failure or wait that has not yet been exposed.

Switch to a new package containing startup diagnostics, fully restart, wait at least 15 seconds, and inspect these logs:

| Log | Meaning and next step |
| --- | --- |
| `STARTUP_FAILED` | An actual initialization exception was observed. Provide the complete log and preceding stage records to locate the failure |
| `STARTUP_WAIT` | No actual ready message has arrived after 15 seconds. Provide its pending and history fields plus subsequent logs; this notice does not stop a slow startup or establish failure |
| `[C3 MiniGame] Construct runtime-ready` | The actual ready message has been handled. Continue checking the first frame, input, and later errors |

The new diagnostics record stages for worker creation, the job scheduler, runtime creation and initialization, project data, Canvas, WebGL, and package-resource reads. They retain the secure-context warning instead of suppressing it or faking ready to make the test appear successful. Failure to read an optional resource alone does not fail startup, and remote application URLs are excluded from diagnostic logs.

If the screen is gray and neither diagnostic appears, keep the startup logs and confirm that the new package is running. Include the TikTok client version and device information in your report. This step gathers the specific failing stage; it is not proof that the gray screen has been fixed. Full records are in [Validation records](../validation/).

## TikTok reports Can only call Window.queueMicrotask on instances of Window

TikTok iOS physical-device diagnostics from `fix2` captured `STARTUP_FAILED` at `runtime-interface-init` with `Can only call Window.queueMicrotask on instances of Window`. The issue was reproduced locally: the old implementation bound an underlying global function to `GameGlobal`, but that function required a real Window as `this`, so message-channel initialization failed. Binding it again to the engine's compatibility object could not undo the first binding.

`fix3` attempted to capture the global environment and `GameGlobal` separately and rebind receivers for functions shared between them. This passed the local simulated-host checks, but the user confirmed the same phone error in the new package marked `build=host-receiver-3`, ruling out accidental use of an old package. Rebinding did not accommodate the actual host. The available evidence is insufficient to confirm whether the phone's `globalThis` is a proxy.

Here, `Window` refers to the underlying function's type check. It does not mean that the full webpage DOM is directly available. The `window` / `self` seen by Construct remain compatibility objects supplied by the adapter; the fix does not introduce a real browser DOM into the mini-game. See TikTok's [Technical Overview](https://developers.tiktok.com/docs/en/mini-games-technical-overview) for limits on full DOM, CSS, and arbitrary browser APIs.

Starting with `fix4` (`build=promise-microtask-4`), TikTok completely skips native `queueMicrotask`, including reading or probing it. A Promise microtask queue is installed as the engine scope is created, so Worker / MessageChannel cannot cache the old function first. Bare calls and `self.queueMicrotask` both use this queue. The latest `fix5` retains this fix.

The queue is asynchronous, preserves enqueue order, returns `undefined`, and ignores callback return values. Invalid callbacks throw `TypeError` synchronously; callback exceptions reach startup diagnostics or error logs. Native methods are not overwritten, and the adapter does not obtain a real DOM through the host's `window` / `document`. Complete-package tests cover a host where the native queue always throws and window/document access also throws; message channels and Workers can complete startup under that contract.

**Later user screenshots of fix4 on a physical device showed the 57-entry API page and navigation into the local-storage category.** This evidence covers only the displayed page and category interaction, not every API. If another environment still shows a gray screen, wait at least 15 seconds and provide the complete new `STARTUP_FAILED` or `STARTUP_WAIT` logs.

## TikTok storage read-back differs after writing

The user reported this on the `fix4` page “本地存储 · localStorage 映射” (Local storage: localStorage mapping). The old adapter first queried `getStorageInfoSync().keys` and immediately returned `null` when the key was absent from that list. Local tests reproduced incorrect read-back when native reads and writes worked but enumeration did not include the new key. The raw return values from the user's phone have not been obtained, so delayed host enumeration must not be described as the confirmed device root cause.

Use `fix5`, or update the source and reconvert, confirming the log marker `build=storage-device-5`. TikTok localStorage and `runtime.storage` now read keys directly through `getStorageSync`; enumeration no longer gates reads. Project-storage `ready()` no longer requires `getStorageInfoSync`, which became available in SDK 0.8.0. localStorage preserves a legitimate empty string and treats `null` / `undefined` as missing. Project-storage values always use a nonempty envelope, so a native empty string also represents missing data there.

Key enumeration, counts, and clearing still depend on actual native enumeration. Missing APIs or failures are reported explicitly. The adapter does not cache written values to manufacture successful read-back. Retest writing, reading, deletion, and reading after restart separately; these phone behaviors still need confirmation. If they fail, keep the error and version information without publicly exposing storage contents or personal credentials.

## TikTok getDeviceInfo is reported as unsupported

The old TikTok directory did not register `getDeviceInfo`, so the bridge could return `UNSUPPORTED` even if the host supplied the function. `fix5` adds a synchronous entry: it prefers `TTMinis.game.getDeviceInfo` and uses a compatibility mapping to the official same-platform `TTMinis.game.getSystemInfoSync` only if the first method is missing or is not a function. When either method is callable, `supportsAPI("getDeviceInfo")` returns true and `getAPISync("getDeviceInfo")` reads the actual native result.

`getDeviceInfo` is not currently listed in the official [System documentation](https://developers.tiktok.com/docs/en/mini-games-sdk-system), so this mapping is disclosed explicitly. For this entry, `nativeMethod` in `getCapabilities()` identifies the selected method, and `compatibilityFallback` indicates use of the compatibility path. Capability queries do not execute native APIs. The original native object is returned unchanged, without adding missing fields or inventing device information. If native `getDeviceInfo` itself throws, the failure is preserved without switching to system information; `UNSUPPORTED` is reported when neither method exists. Device readings from the new package still need phone retesting.

## TikTok host is not detected, or payment does not fulfill an order

Confirm that the target is TikTok Native Mini Games and select the `tiktok` platform. TikTok's namespace is `TTMinis.game`. Do not inject or rename Douyin's `tt` to simulate support. The native runtime does not need `TTMinis.game.init()`. The HTML-runtime SDK-loading procedure does not apply to native converted output.

Even APIs with matching names must follow the TikTok-specific directory contract. Unregistered top-level methods are not automatically forwarded. Methods on file managers, audio objects, or SocketTask must be called on the returned object.

Client payment success / complete does not mean the order is confirmed or fulfilled. Check whether your server received the Webhook, verified the signature against the original body, validated the merchant and environment, and updated the order idempotently. Then check that the client queries your own authenticated order endpoint. A polling timeout remains pending; it does not automatically mark failure or charge again. Create a new order for a purchase after user cancellation or failure. See [TikTok payment integration](../tiktok-iap/). This project has TikTok iOS user screenshots providing page-display and category-navigation evidence, as well as startup and storage failure records. TikTok IDE, complete physical-device functionality, and real-payment acceptance remain outstanding.
